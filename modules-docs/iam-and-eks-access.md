# Module: Identity and Access Management (IAM) & EKS Cluster Access

This document captures the **concepts** behind how identities are authenticated and
authorized against an Amazon EKS cluster. It pairs with the hands-on command logged in
[`command-log/commands/04-eks-get-token-decode.md`](../command-log/commands/04-eks-get-token-decode.md).

---

## 1. What is AWS IAM?

**AWS Identity and Access Management (IAM)** is an AWS service that performs two essential
functions:

- **Authentication** — verifying *who you are* (the identity).
- **Authorization** — governing *what actions* that identity is allowed to perform.

Within AWS, a **resource** can be:
- Another AWS service (e.g. EC2), or
- An AWS **principal** such as an IAM **User** or **Role**.

The rules governing what actions a resource may perform are expressed as **IAM policies**
(JSON documents listing allowed/denied actions).

> Beginner analogy: Authentication is showing your ID card at the door (proving who you
> are). Authorization is the list on the wall saying which rooms your badge can open.

## 2. Controlling Access to Amazon EKS Clusters

There are **three mechanisms** for granting an identity access to an EKS cluster. Knowing
which is which is half the lesson:

| Mechanism | Status | When to use it | Taught in |
|-----------|--------|----------------|-----------|
| **aws-auth ConfigMap** | Legacy (still supported) | Older clusters; you'll encounter it in existing environments | IAM Groups and Roles |
| **EKS access entries** | **Current recommendation** | New clusters; what EKS Auto Mode itself uses for its nodes | Cluster Access Management Controls |
| **OIDC identity provider** | For external IdPs | Users authenticated by Cognito, Okta, etc. instead of IAM | OIDC Identity Provider Authentication |

We teach the **legacy aws-auth path first** because you will meet it in real
environments — but for anything new, **access entries** are the mechanism to reach for.

> This maps directly to our Terraform: the primary `eks-auto` cluster is configured with
> `authentication_mode = "API_AND_CONFIG_MAP"` precisely so both the legacy ConfigMap
> labs *and* the modern access-entry labs work. See the root `main.tf`.

## 3. How authentication actually works on EKS

The Kubernetes project supports several strategies to authenticate requests to the
**kube-apiserver** (the cluster's API "front door"): Bearer Tokens, X.509 certificates,
OIDC, etc. Amazon EKS natively supports:
- **Webhook token authentication**
- **Service account tokens**
- **OIDC authentication** (since February 21, 2021)

### The webhook token flow (IAM → Kubernetes)

The webhook authentication strategy calls a webhook that verifies **bearer tokens**. On
Amazon EKS:

1. When you run a `kubectl` command, a bearer token is generated by the **AWS CLI** (or
   the `aws-iam-authenticator` client).
2. The token is passed to the **kube-apiserver**, which forwards it to the
   **authentication webhook**.
3. If the request is well-formed, the webhook calls a **pre-signed URL** embedded in the
   token's body.
4. That URL validates the request's signature and returns information about the user
   (account, ARN, UserId) back to the kube-apiserver.

The result: your **AWS identity** is translated into a **Kubernetes identity**, so IAM
effectively decides who can talk to the cluster.

### What the token looks like

Each token starts with `k8s-aws-v1.` followed by a base64-encoded string. That encoded
string, when decoded, is a **pre-signed STS `GetCallerIdentity` URL** — essentially a
signed "ask AWS who I am" request the webhook can safely call to confirm your identity.

See the hands-on decode in
[`04-eks-get-token-decode.md`](../command-log/commands/04-eks-get-token-decode.md).
